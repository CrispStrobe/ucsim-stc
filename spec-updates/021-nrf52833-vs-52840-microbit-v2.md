# 021 — nRF52833 vs nRF52840 delta for micro:bit V2 feasibility

## Context

The micro:bit V2 uses the **nRF52833** (Cortex-M4F, 512 KB flash, 128 KB RAM).
labwired-core has a silicon-verified **nRF52840** model (Cortex-M4F, 1024 KB flash,
256 KB RAM).  This report assesses whether the 52840 model can serve as a
stand-in for the 52833 in course-style programs, and what the honest labeling
would be.

## Execution proof (2026-08-15)

Two clean-room bare-metal ARM Thumb-2 programs built with `arm-none-eabi-as`
ran correctly under labwired's nRF52840 model:

1. **UART hello** (`uart_hello.S`): configures UART0 (ENABLE, PSELTXD, BAUDRATE,
   STARTTX, TXD/TXDRDY), outputs `nRF52840 OK\n`.  Stdout captured by labwired.
2. **GPIO toggle + UART** (`gpio_toggle_uart.S`): configures P0.13 output via
   DIRSET (0x50000518), toggles via OUTSET (0x50000508) / OUTCLR (0x5000050C)
   with a 100-iteration delay loop, reports each edge over UART.  8 edges
   (H L H L H L H L), then DONE.

Test: `tests/rung_nrf52840_bare.sh` — 5/5 pass.

## nRF52833 vs nRF52840: the delta

| Property | nRF52833 | nRF52840 | Impact |
|---|---|---|---|
| **Core** | Cortex-M4F | Cortex-M4F | **Identical** |
| **Flash** | 512 KB | 1024 KB | Size only — no register diff |
| **RAM** | 128 KB | 256 KB | Size only — no register diff |
| **GPIO ports** | P0 (32 pins) + P1 (10 pins) | P0 (32 pins) + P1 (16 pins) | P1.10–P1.15 absent on 52833; course programs use P0 only |
| **UART** | UARTE0, UARTE1 | Same | **Identical peripheral** |
| **I2C/TWI** | TWIM0/1, TWIS0/1 | Same | **Identical peripheral** |
| **SPI** | SPIM0/1/2/3, SPIS0/1/2 | Same (52840 adds SPIM3 EASYDMA) | Course programs don't use SPI3 |
| **Timer** | TIMER0–4 | Same | **Identical peripheral** |
| **RTC** | RTC0–2 | Same | **Identical peripheral** |
| **PWM** | PWM0–3 | Same | **Identical peripheral** |
| **SAADC** | Yes (8 channels) | Yes (8 channels) | **Identical peripheral** |
| **GPIOTE** | 8 channels | 8 channels | **Identical peripheral** |
| **USB** | Yes (USBD) | Yes (USBD) | **Identical register set** |
| **QSPI** | ❌ Absent | Yes | Not used by micro:bit programs |
| **NFC** | Yes (NFCT) | Yes (NFCT) | **Identical peripheral** |
| **Cryptocell** | CC310 (subset) | CC310 | Same base; 52833 lacks some algorithms |
| **FPU** | Yes | Yes | **Identical** |
| **FICR** | INFO.PART=0x00052833 | INFO.PART=0x00052840 | Firmware that checks PART will see the wrong ID |
| **Peripheral addresses** | Same base addresses | Same base addresses | **Register-compatible** |
| **Clock** | 64 MHz HFCLK, 32.768 kHz LFCLK | Same | **Identical** |

### Summary of differences that matter

1. **FICR INFO.PART**: 0x00052833 vs 0x00052840.  Any firmware that reads
   FICR to identify the chip will see the wrong part number.  This includes
   Nordic SDK's `nrf_drv_check` and Zephyr's `DT_SOC_SERIES`.  Mitigation:
   patch the FICR value in a 52833 chip YAML (trivial — one register override).

2. **GPIO P1 pin count**: 52833 has 10 pins (P1.0–P1.9), 52840 has 16.
   micro:bit V2 only uses P0 for LEDs and buttons; the extra P1 pins are
   irrelevant for course programs.

3. **QSPI**: 52840 has QSPI, 52833 does not.  No micro:bit program uses QSPI.

4. **Flash/RAM size**: 52833 is smaller.  A chip YAML can constrain these.

**Everything else is register-compatible at the same addresses.**

## Verdict: can the 52840 model serve as a stand-in?

**Yes, with a simple chip YAML for nRF52833.**

The peripherals are register-compatible at the same addresses.  A `nrf52833.yaml`
chip config would:
- Set `flash.size: "512KB"`, `ram.size: "128KB"`
- Override FICR INFO.PART to 0x00052833
- Omit QSPI
- Constrain GPIO P1 to 10 pins

Everything else — GPIO, UART, TIMER, TWI, PWM, SAADC — inherits from the
52840 model unchanged, which is already silicon-verified with 11 passing suites.

**Honest labeling**: "nRF52833 model derived from the silicon-verified nRF52840;
peripherals register-compatible at identical addresses; FICR overridden;
flash/RAM constrained; GPIO P1 pin count reduced.  Not independently
silicon-verified — the 52840 capture is the oracle."

## Decision for task #18

**labwired-now, not blocked-on-upstream.**  The run path is:

1. Create `configs/chips/nrf52833.yaml` (20-line delta from 52840)
2. Course programs compile with `arm-none-eabi-gcc` targeting Cortex-M4
3. Run under labwired with the 52833 chip config
4. GPIO edges captured via UART-based reporting (gpio-trace not yet wired
   for the nRF GPIO model — a labwired enhancement, not a blocker)

The gap is **gpio-trace integration**: labwired's `--gpio-trace` flag does not
produce output for the nRF52840 GPIO model (tested 2026-08-15; the `gpio` type
is declarative register storage without side-effect event emission).  This
means GPIO edge timing must be verified via UART-reported state transitions
rather than direct pin-edge capture.  For course-style programs that toggle
LEDs and read buttons, this is sufficient.  For timing-critical validation
(NeoPixel-grade), the GPIO model would need event hooks — a labwired
enhancement request, not a blocker for the ASM execution path.
